# Guarded node maintenance

## What is automated

`.github/workflows/node-maintenance.yaml` checks official RKE2 releases daily
and opens review-only PRs containing exact versions and publisher archive
SHA256 pins. It explicitly dispatches CI because PR events generated by
`GITHUB_TOKEN` do not start other workflows. The repository must permit
Actions to create pull requests. Nothing auto-merges or connects GitHub
hosted runners to the cluster.

The local Python 3.11+ runner uses existing `kubectl`, OpenSSH and interactive
sudo. It does not install a runner, collect passwords, change sudoers, export
kubeconfigs or put cluster credentials in GitHub. Run from a real terminal;
keep it open throughout maintenance. Do not pipe its input or run `apply`
through an assistant's noninteractive command runner.

Ubuntu stays on **26.04 LTS**, with its supported `linux-generic` kernel
metapackage. No mainline/PPA kernels, interim-release upgrade, package purge,
autoremove, replica reduction or eviction/PDB bypass is performed. Existing
unattended security updates remain enabled; GitHub cannot discover private
host APT state. Run `audit` and `plan` locally for OS updates/reboot state.
The kernel pin must be reviewed against refreshed Ubuntu APT metadata before
each OS run; discovery currently automates RKE2 pins, not Ubuntu kernel pins.

## Maintenance stages

1. OS/kernel/headless maintenance: worker2 canary, worker1, controller.
2. RKE2 1.36: server first, worker2, worker1.
3. RKE2 1.37: a separate plan after the entire 1.36 fleet is accepted.

The initial proposals are RKE2 `v1.36.6+rke2r1`, then `v1.37.2+rke2r1`,
and Ubuntu kernel `7.0.0-43-generic`. These are **proposals, not deployment
clearance**. Review target release notes and the actual Canal/CoreDNS,
Longhorn/CSI, Kyverno, Traefik, Intel GPU and Ubuntu combinations before
using `--compatibility-reviewed`. An OS support matrix is not evidence that
all installed addons support that Kubernetes version. Major etcd transitions
also need backup-tool compatibility review.

The intentionally cordoned controller stays cordoned. Kured stays suspended.
The sole control-plane restart/reboot causes an API/etcd interruption.
Workloads continue only where their placement and dependencies permit it;
this is not a zero-downtime guarantee.

## Planning and approval

From the repository root in PowerShell:

```powershell
python -B .github\scripts\node-maintenance.py audit
python -B .github\scripts\node-maintenance.py plan --action os --output "$env:TEMP\homelab-os-plan.json"
Get-Content "$env:TEMP\homelab-os-plan.json"
```

`plan` is read-only and prints the plan's SHA256, blast radius and blockers.
It binds approval to the cluster UID, code/policy bytes, boot IDs, source
versions and simulated package candidates. Plans expire after four hours.
Store plans outside Git; they contain technical metadata, not records,
credentials or raw workload logs.

Resolve every blocker before approval. In particular:

- Single-replica zero-disruption PDBs must be redesigned with real maintenance
  capacity or explicitly reviewed application availability changes, not
  bypassed with `--disable-eviction` or force deletion.
- A hostname-pinned application such as Plex cannot simply migrate during
  its host's drain. GPU/data-locality and acceptable application downtime
  require a separate placement/maintenance design.
- The conservative capacity check counts resource requests, init containers,
  extended resources and pod slots on the other worker. Affinity/topology,
  hostPath and PV locality constraints block rather than being guessed safe.
  It does not claim to emulate the Kubernetes scheduler.
- All active pods, native HTTPS/VPN probes, both Longhorn managers, and every
  active Longhorn volume must pass. Attached volumes need two running RW worker
  copies; detached volumes need two clean stopped worker copies. The two
  explicitly listed historical finance volumes retain their separate
  stopped-replica quarantine: exact volume/replica/engine identities and data
  directories are bound in the plan, and empty attachment tickets and stopped,
  detached, unsalvaged state are rechecked throughout. They are never attached,
  salvaged or treated as healthy two-copy volumes.
- APT metadata must be recent. The host refreshes APT again before upgrading;
  changed package candidates abort, requiring a new reviewed plan.

## Controller recovery prerequisite

Provision a **trusted off-node NFS/CIFS recovery mount on the controller**,
with an already existing root-owned mode-0700 recovery subdirectory. Do not
reuse a public media directory. Ensure the storage server enforces private
access too; client mode bits alone are not a server-side confidentiality
guarantee. NFS root-squash may require server-side provisioning.

The workflow requires its path through `--recovery-directory`; there is no
invented default or fallback to the controller's local disk. It creates a
fresh local RKE2 snapshot, validates its appended SHA256 and native database
status with a hash-pinned, network-isolated `etcdutl`, then writes and reopens
a mode-0600 off-node copy and verifies its checksum. The tool pin follows the
currently running etcd minor (3.6 or 3.7), including after the RKE2 1.37
transition. Snapshot contents never
leave the cluster for GitHub or the workstation.

The operator must separately verify an existing secure backup of the RKE2
server token, required for recovery, and acknowledge this with
`--token-backup-confirmed`. This tool does not read/copy that token. Snapshot
integrity/native status is **not** a restore rehearsal. The current supported
layout is the existing tarball RKE2 install and default data/snapshot paths;
custom layouts stop rather than guessing.

After resolving blockers and reviewing the complete plan, replace the
placeholders below. **Do not run while a plan contains blockers.**

```powershell
python -B .github\scripts\node-maintenance.py apply --plan "$env:TEMP\homelab-os-plan.json" --approve <PLAN_SHA256> --recovery-directory <PROTECTED_HOST_MOUNT_DIRECTORY> --token-backup-confirmed
```

For each minor upgrade, create a fresh plan, review compatibility, then apply:

```powershell
python -B .github\scripts\node-maintenance.py plan --action rke2 --minor 1.36 --output "$env:TEMP\homelab-rke2-plan.json"
Get-Content "$env:TEMP\homelab-rke2-plan.json"
python -B .github\scripts\node-maintenance.py apply --plan "$env:TEMP\homelab-rke2-plan.json" --approve <PLAN_SHA256> --recovery-directory <PROTECTED_HOST_MOUNT_DIRECTORY> --token-backup-confirmed --compatibility-reviewed
```

Repeat with `--minor 1.37` only after complete 1.36 acceptance. Minor skipping,
downgrades and starting a new fleet run in mixed-version recovery state are
rejected.

## Headless server profile

The OS stage sets `multi-user.target` and masks/stops the display manager,
CUPS services/socket/path, Bluetooth, Avahi and ModemManager. This terminates
desktop sessions and disables printing, mDNS advertisement and modem use.
Desktop packages remain installed: package removal needs a separately
reviewed simulation/list, not a blanket `ubuntu-*` purge.

NetworkManager, systemd-networkd, SSH, AppArmor, time synchronization, thermal
management, iSCSI/NFS, firmware and Intel GPU drivers are preserved. In
particular, NetworkManager currently owns the controller and worker2 uplinks.
Do not substitute a networking migration for headless cleanup.

## Execution and failure behavior

An exclusive non-expiring ConfigMap lock in `kube-system` serializes runs.
Before disruption the workstation captures pod identities, termination states,
mount metadata and event/log classification counts in a printed temporary
evidence directory. Raw logs, event messages and secret/record payloads are
never written. The host retains private technical state/journal counts too.
Each node gets bounded eviction-based drain, a privileged host step, host/API
recovery checks, then full native/storage acceptance. Three stable health
samples bracket steps. OS acceptance requires a different boot ID, the exact
approved running kernel, no remaining reboot sentinel and headless default.
RKE2 acceptance binds the running host executable and kubelet version.

Worker uncordon happens only after host/Ready acceptance; the full postflight
then checks workload recovery. A failed postflight re-cordons that worker.
No error path automatically uncordons the current failed node or continues
to the next. Drain can evict some workloads before failing; inspect it.

RKE2 stop uses `SendSIGKILL=no` and a five-minute graceful-stop guard, not a
killall fallback. The guard stays after failures. Previous public RKE2
binaries, protected snapshots and technical receipts are retained; there is
no automatic Kubernetes/etcd downgrade or restore.

Privileged steps run in named host systemd units, not an SSH session's process
tree. If the workstation disconnects, inspect the printed run's host unit and
receipt before any recovery action. A package upgrade is not killed merely
because a workstation wait expires; the non-expiring fleet lock still prevents
another workflow from starting.

After an interruption **do not blindly rerun**. Capture events, termination
state, mounts and service status; recover the failed node under the normal
runbook. Inspect the lock's `run_id`, reconcile the actual cordon/version
state, and only then deliberately release that specific lock. A stale lock
has no timer that can start a second run while the controller is offline.

Successful RKE2 steps remove only their own temporary graceful-stop guard.
Successful fleet completion releases its owned lock. Cleanup of old root-only
maintenance directories/backups is an explicit retention task, never broad
recursive deletion.

## Verification

```powershell
python -B .github\scripts\test-node-maintenance.py
```

CI tests unsupported minor jumps, approval tampering/expiry/context,
zero-budget PDB detection, capacity/placement constraints, two-copy storage,
snapshot corruption, package drift, preserved server services and fail-stop
behavior. They do not execute privileged maintenance or claim a live reboot
rehearsal.
