# Guarded node maintenance

## What is automated

`.github/workflows/node-maintenance.yaml` checks official RKE2 releases daily
and opens review-only PRs containing exact versions and publisher archive
SHA256 pins. It explicitly dispatches CI because PR events generated by
`GITHUB_TOKEN` do not start other workflows. The repository must permit
Actions to create pull requests. Nothing auto-merges or connects GitHub
hosted runners to the cluster.

The local Python 3.11+ runner uses existing `kubectl`, OpenSSH and interactive
sudo. It does not install a runner, collect passwords, change sudoers, export
kubeconfigs or put cluster credentials in GitHub. Run from a real terminal;
keep it open throughout maintenance. Do not pipe its input or run `apply`
through an assistant's noninteractive command runner.

Application downtime, including multiple applications together, is accepted.
The maximum restoration budget is **12 hours**. The runner starts this clock
conservatively at lock acquisition, before any drain, and persists the UTC start
and deadline in the non-expiring lock and local technical evidence. It reserves
the final two hours for recovery instead of starting another disruptive step.
Wall-clock and monotonic elapsed time are both checked; clock rollback cannot
extend a running batch. A failed/interrupted run cannot reset the clock by
starting another run because its lock remains held.

Recovery waits and each host's pre-mutation gate honor this deadline. Reaching
the reserve stops new disruption; it does not kill an in-progress package
manager, forcibly reboot a host, or perform an automatic restore. This is a
fail-stop recovery budget, not an unconditional guarantee after hardware
failure. Do not start without a credible recovery path inside the limit.
Application downtime consent does not bypass PDB, storage or locality gates:
those still require exact workload-specific maintenance design.

Ubuntu stays on **26.04 LTS**, with its supported `linux-generic` kernel
metapackage. No mainline/PPA kernels, interim-release upgrade, package purge,
autoremove, replica reduction or eviction/PDB bypass is performed. Existing
unattended security updates remain enabled; GitHub cannot discover private
host APT state. Run `audit` and `plan` locally for OS updates/reboot state.
The kernel pin must be reviewed against refreshed Ubuntu APT metadata before
each OS run; discovery currently automates RKE2 pins, not Ubuntu kernel pins.

Existing reboot alerts consume `kured_reboot_required`. With Kured suspended,
that series can be absent, which is not the same as a zero reboot requirement.
`NodeRebootTelemetryMissing` compares it with the Kubernetes node inventory and
warns per missing node. This exposes the monitoring gap; it does not collect
host package/kernel state or prove patch compliance. Until independent host
telemetry is provisioned, use the read-only local `audit` for those facts.
Do not enable Kured solely to restore this metric.

## Maintenance stages

1. OS/kernel/headless maintenance: worker2 canary, worker1, controller.
2. RKE2 1.36: server first, worker2, worker1.
3. RKE2 1.37: a separate plan after the entire 1.36 fleet is accepted.

The initial proposals are RKE2 `v1.36.6+rke2r1`, then `v1.37.2+rke2r1`,
and Ubuntu kernel `7.0.0-44-generic`. These are **proposals, not deployment
clearance**. Review target release notes and the actual Canal/CoreDNS,
Longhorn/CSI, Kyverno, Traefik, Intel GPU and Ubuntu combinations before
using `--compatibility-reviewed`. An OS support matrix is not evidence that
all installed addons support that Kubernetes version. Major etcd transitions
also need backup-tool compatibility review.

The intentionally cordoned controller stays cordoned. Kured stays suspended.
The sole control-plane restart/reboot causes an API/etcd interruption.
Workloads continue only where their placement and dependencies permit it;
this is not a zero-downtime guarantee.

## Planning and approval

From the repository root in PowerShell:

```powershell
python -B .github\scripts\node-maintenance.py audit
python -B .github\scripts\node-maintenance.py plan --action os --output "$env:TEMP\homelab-os-plan.json"
Get-Content "$env:TEMP\homelab-os-plan.json"
```

`plan` is read-only and prints the plan's SHA256, blast radius and blockers.
It binds approval to the cluster UID, code/policy bytes, boot IDs, source
versions, actual kubectl/API versions and simulated package candidates. Plans expire after four hours.
Store plans outside Git; they contain technical metadata, not records,
credentials or raw workload logs.

For OS maintenance of worker2 without attempting worker1 or the controller, add
`--worker2-only` to `plan`. The selection is part of the approval hash and is
preserved when `apply` rebuilds the plan. It cannot be used for RKE2 upgrades,
which retain the controller-first minor-upgrade sequence. Only worker2's
eviction/host steps are selected; all nodes, storage copies, quarantines,
workload health, package bindings and recovery-access checks are still checked.
Worker1-only eviction blockers do not become worker2 blockers, but this flag
does not waive any worker2 capacity, PDB, placement or native-storage gate.
The scope remains held source, not a drain/reboot approval.

For cold-stop preparation, `cold-inventory --output <new-file>` captures a
read-only restoration inventory and refuses to overwrite an existing receipt.
It discovers bound Longhorn claims (including idle application namespaces) and
active users, captures their Deployment/StatefulSet cohort, and records exact
UIDs/specification hashes and original
replica counts, including zero. It also records KEDA/HPA ownership, scheduled
jobs and original Flux suspension states. Only technical bindings and selected
restoration fields are saved, not workload templates, environment values or
credentials. Scale-down PVC deletion policies are rejected; unmatched HPA
owners and active jobs remain explicit blockers.

This command does not suspend, scale, change PDBs or create a disruption window.
Its `cold-inventory` action is deliberately not accepted by `apply`. Cold-stop
execution still needs reviewed autoscaler/operator ordering, complete
infrastructure/native storage contracts, and durable recovery independent of
the workstation. Keep two clean detached storage copies rather than treating
this inventory as permission for temporary single-replica writes.

The held KEDA core HelmRelease pins chart 2.21.1 and all three core images to
the same platform manifests used by the accepted native HTTP add-on fixture
in `apps\_shared\http-addon-owned\source.json`. A running multi-platform image
index may differ from its pinned `linux/amd64` child digest; verify the hashed
index-to-manifest relationship instead of treating that difference as a foreign
image. Keep chart/image pins synchronized with native acceptance. These source
pins do not imply that production's current tag-only image references have
already been reconciled.

Resolve every blocker before approval. In particular:

- The workstation's `kubectl` must be within one minor of both the current API
  and the proposed API after an RKE2 upgrade. The plan reads actual client/server
  versions and rechecks them before acquiring the lock. A compatible client
  change requires a fresh plan too. The observed Windows client `v1.34.2`
  can inspect the existing 1.35 API but cannot perform the 1.36 upgrade; a 1.36
  client covers the planned 1.35 -> 1.36 -> 1.37 API sequence. Blindly installing
  the newest client is not safe either if it is too far ahead of the current
  API. See the [official version-skew policy](https://kubernetes.io/releases/version-skew-policy/#kubectl).
- Single-replica zero-disruption PDBs must be redesigned with real maintenance
  capacity or explicitly reviewed application availability changes, not
  bypassed with `--disable-eviction` or force deletion.
  The held source proposal changes only 14 reviewed singleton budgets to
  `maxUnavailable: 1`: cert-manager's three components, four Flux controllers,
  sealed-secrets, Traefik, the MetalLB controller, Prometheus, Alertmanager,
  Grafana and Loki. Their existing `minAvailable: 50%` rounds up to one and
  permits no healthy singleton eviction. This proposal explicitly allows a
  singleton to be fully unavailable under normal voluntary eviction; it is a
  persistent availability-policy change, **not** a maintenance-window lock.
  Selectors and all Longhorn/CSI/Kyverno, DaemonSet and unmatched legacy budgets
  remain unchanged. No replica count, eviction privilege or drain bypass is
  added. Keep this proposal unmerged until the complete maintenance profile
  is reviewed; it does not solve capacity, quiescence, locality or recovery.
- A hostname-pinned application such as Plex cannot simply migrate during
  its host's drain. The held Plex downtime contract below treats its exact
  replacement as expected Pending on worker1 instead of claiming GPU migration.
- The conservative capacity check counts resource requests, init containers,
  extended resources and pod slots on the other worker. Required node affinity
  is checked against the actual peer's labels/name: terms are ORed and each
  term's expressions/fields are ANDed. Label `In`, `NotIn`, `Exists` and
  `DoesNotExist`, and `metadata.name` field `In`/`NotIn` are supported.
  Unsupported operators/fields and empty required terms remain blocked.
  Required inter-pod affinity/anti-affinity, hard topology spread, hostPath and
  PV locality still require explicit design. This does not claim to emulate
  the Kubernetes scheduler or relax any workload's actual placement policy.
- The four reviewed Longhorn CSI sidecar Deployments (`csi-attacher`,
  `csi-provisioner`, `csi-resizer`, `csi-snapshotter`) use only the driver's
  local UNIX socket, not application data. This exact
  `/var/lib/kubelet/plugins/driver.longhorn.io` mount is reviewed separately:
  the plan binds each Pod through its actual ReplicaSet/Deployment UIDs and
  desired-template hash, exact volume type/mount, and current image. These
  bindings are checked again before lock acquisition. This does not bypass
  their capacity, scheduling or PDB checks. NFS controller
  `/var/lib/kubelet/pods` bidirectional mounts, Longhorn instance-manager data
  paths and all other hostPath uses still require explicit review. Plex's
  exact devices are covered only by its separately hash-bound downtime contract.
- Longhorn instance-manager budgets are a separate native drain lifecycle.
  The [pinned 1.12.1 controller](https://github.com/longhorn/longhorn-manager/blob/8320238242e8c804325d9588ec1db10feb9f36b8/controller/instance_manager_controller.go#L1303-L1394)
  creates `minAvailable: 1` before cordon and decides whether to remove it
  after cordon. Its removal checks include no local engines/frontends and a
  healthy replica protected by another schedulable node's PDB under the
  retained `block-if-contains-last-replica` policy. Do not lower/delete these
  budgets, invent missing owner references, or treat a matching name/label
  as permission to ignore them. The runner has no reviewed deferred-PDB or
  stateful-quiescence path yet; these remain real maintenance blockers.
- All active pods, native HTTPS/VPN probes, both Longhorn managers, and every
  active Longhorn volume must pass. Attached volumes need two running RW worker
  copies; detached volumes need two clean stopped worker copies. The two
  explicitly listed historical finance volumes retain their separate
  stopped-replica quarantine: exact volume/replica/engine identities and data
  directories are bound in the plan, and empty attachment tickets and stopped,
  detached, unsalvaged state are rechecked throughout. They are never attached,
  salvaged or treated as healthy two-copy volumes.
- APT metadata must be recent. The host refreshes APT again before upgrading;
  changed package candidates abort, requiring a new reviewed plan.

### Held Plex downtime contract

The `plex_downtime` policy hashes freeze the reviewed single-replica Plex
StatefulSet template and admitted Pod specification. A plan binds its actual
controller UID/generation, stable revision and original Pod UID. Only the exact
`media/plex-plex-media-server-0` workload pinned to worker1 is excluded from
peer-worker migration capacity/scheduling checks; it is not a generic hostPath,
GPU, namespace or unhealthy-Pod exemption. PVC locality and PDB checks remain.
Hashes change on image, init-container, volume, mount, resource, security or
other specification drift and require a new source review. Only `nodeName` and
the API-generated service-account projection suffix are normalized.

Before the drain Plex must be Ready and its binding must still match. After a
normal worker1 eviction, the runner waits within the existing outage budget for
the exact unscheduled replacement to report Pending/Unschedulable with a new
Pod UID but unchanged controller/revision/specification. Only then may its
readiness and `https://plex.homelab/identity` probe be omitted for that worker1
post-drain check. Missing, terminating, scheduled, Running-but-unhealthy,
modified or unrelated Pods are not accepted. The other node steps have no
Plex exception.

All native Longhorn two-copy/quarantine, manager, peer-node, other-workload and
VPN/probe checks still run before host changes. After worker1 returns and is
uncordoned, full readiness and the real Plex probe are required again before
another node or lock release. The review does not scale Plex, change PDBs,
move its GPU/media/config data, waive storage protection, reset an outage clock
or authorize a maintenance window. This remains held source pending protected
live drain/recovery acceptance; it does not solve the other fleet blockers.

## Controller recovery prerequisite

Provision a **trusted off-node NFS/CIFS recovery mount on the controller**,
with an already existing root-owned mode-0700 recovery subdirectory. Do not
reuse a public media directory. Ensure the storage server enforces private
access too; client mode bits alone are not a server-side confidentiality
guarantee. NFS root-squash may require server-side provisioning.

The workflow requires its path through `--recovery-directory`; there is no
invented default or fallback to the controller's local disk. It creates a
fresh local RKE2 snapshot, validates its appended SHA256 and native database
status with a hash-pinned, network-isolated `etcdutl`, then writes and reopens
a mode-0600 off-node copy and verifies its checksum. The tool pin follows the
currently running etcd minor (3.6 or 3.7), including after the RKE2 1.37
transition. Snapshot contents never
leave the cluster for GitHub or the workstation.

The operator must separately verify an existing secure backup of the RKE2
server token, required for recovery, and acknowledge this with
`--token-backup-confirmed`. This tool does not read/copy that token. Snapshot
integrity/native status is **not** a restore rehearsal. The current supported
layout is the existing tarball RKE2 install and default data/snapshot paths;
custom layouts stop rather than guessing.

The controller's off-node directory mount, owner and mode are checked through
read-only SSH **before any node is cordoned**, even for a worker-first OS run.
This stops a missing recovery destination before worker disruption rather than
discovering it only when the controller's snapshot stage is reached. The
privileged snapshot stage repeats these checks and verifies the actual copy.

After resolving blockers and reviewing the complete plan, replace the
placeholders below. **Do not run while a plan contains blockers.**

```powershell
python -B .github\scripts\node-maintenance.py apply --plan "$env:TEMP\homelab-os-plan.json" --approve <PLAN_SHA256> --recovery-directory <PROTECTED_HOST_MOUNT_DIRECTORY> --token-backup-confirmed
```

For each minor upgrade, create a fresh plan, review compatibility, then apply:

```powershell
python -B .github\scripts\node-maintenance.py plan --action rke2 --minor 1.36 --output "$env:TEMP\homelab-rke2-plan.json"
Get-Content "$env:TEMP\homelab-rke2-plan.json"
python -B .github\scripts\node-maintenance.py apply --plan "$env:TEMP\homelab-rke2-plan.json" --approve <PLAN_SHA256> --recovery-directory <PROTECTED_HOST_MOUNT_DIRECTORY> --token-backup-confirmed --compatibility-reviewed
```

Repeat with `--minor 1.37` only after complete 1.36 acceptance. Minor skipping,
downgrades and starting a new fleet run in mixed-version recovery state are
rejected.

## Headless server profile

The OS stage sets `multi-user.target` and masks/stops the display manager,
CUPS services/socket/path, Bluetooth, Avahi and ModemManager. This terminates
desktop sessions and disables printing, mDNS advertisement and modem use.
Desktop packages remain installed: package removal needs a separately
reviewed simulation/list, not a blanket `ubuntu-*` purge.

NetworkManager, systemd-networkd, SSH, AppArmor, time synchronization, thermal
management, iSCSI/NFS, firmware and Intel GPU drivers are preserved. In
particular, NetworkManager currently owns the controller and worker2 uplinks.
Do not substitute a networking migration for headless cleanup.

## Execution and failure behavior

An exclusive non-expiring ConfigMap lock in `kube-system` serializes runs.
Before disruption the workstation captures pod identities, termination states,
mount metadata and event/log classification counts in a printed temporary
evidence directory. Raw logs, event messages and secret/record payloads are
never written. The host retains private technical state/journal counts too.
Each node gets bounded eviction-based drain, a privileged host step, host/API
recovery checks, then full native/storage acceptance. Three stable health
samples bracket steps. After a successful drain, a new full health check must
pass before the privileged host step: only the selected maintenance node may
have an additional cordon, no active evictable pods may remain there, and peer
readiness/pressure, workloads, strict two-copy storage, quarantines, managers
and native probes are checked again. The technical-only `*-after-drain.json`
receipt records that result. A successful drain exit is not storage or service
acceptance. Failure retains the lock and cordon and never starts the host step.
This does not permit previously unapproved Pending workloads or relax the
separate PDB/locality/downtime-design blockers.

OS acceptance requires a different boot ID, the exact
approved running kernel, no remaining reboot sentinel and headless default.
RKE2 acceptance binds the running host executable and kubelet version.

Worker uncordon happens only after host/Ready acceptance; the full postflight
then checks workload recovery. A failed postflight re-cordons that worker.
No error path automatically uncordons the current failed node or continues
to the next. Drain can evict some workloads before failing; inspect it.

RKE2 stop uses `SendSIGKILL=no` and a five-minute graceful-stop guard, not a
killall fallback. The guard stays after failures. Previous public RKE2
binaries, protected snapshots and technical receipts are retained; there is
no automatic Kubernetes/etcd downgrade or restore.

Privileged steps run in named host systemd units, not an SSH session's process
tree. If the workstation disconnects, inspect the printed run's host unit and
receipt before any recovery action. A package upgrade is not killed merely
because a workstation wait expires; the non-expiring fleet lock still prevents
another workflow from starting.

After an interruption **do not blindly rerun**. Capture events, termination
state, mounts and service status; recover the failed node under the normal
runbook. Inspect the lock's `run_id`, reconcile the actual cordon/version
state, and only then deliberately release that specific lock. A stale lock
has no timer that can start a second run while the controller is offline.

Successful RKE2 steps remove only their own temporary graceful-stop guard.
Successful fleet completion releases its owned lock. Cleanup of old root-only
maintenance directories/backups is an explicit retention task, never broad
recursive deletion.

## Verification

```powershell
python -B .github\scripts\test-node-maintenance.py
```

CI tests unsupported minor jumps, approval tampering/expiry/context,
zero-budget PDB detection, capacity/placement constraints, two-copy storage,
snapshot corruption, package drift, preserved server services and fail-stop
behavior, including storage/health drift after a successful drain. They do not
execute privileged maintenance or claim a live reboot
rehearsal.
